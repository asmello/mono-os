# Retargeting mono-os from x86_64 to ARM Cortex-M3 (with M4F door open)

## Context

`mono-os` is a Rust bare-metal x86_64 kernel following Phil Opp's "Writing an OS in Rust", through chapter 9 (heap + async). It uses `bootloader_api` 0.11, targets `x86_64-unknown-none`, and depends on x86 features that **do not exist on Cortex-M3/M4**: GDT/TSS, IDT, 8259 PIC, MMU paging, port I/O.

Goals for the port:

- **Primary target**: Cortex-M3 in QEMU (`lm3s6965evb`). Leave the door open for STM32F429ZI Nucleo-144 (M4F) and mbed LPC1768 (M3) without optimising for them.
- **Repo shape**: `dev` was renamed to `x86` (history preserved). ARM work happens on a new branch `arm`. No parallel maintenance.
- **In scope**: boot, timer interrupt, **real UART** (not just semihosting — visibility on hardware matters), tests.
- **Out**: VGA, keyboard, paging, multiprocess.
- **De-emphasised**: heap (sparingly, feature-gated), async executor (only if IRQ-driven I/O later demands it).
- **Curiosity track**: ethernet, without adopting Embassy.
- **End goal**: run a single userspace program with maximum determinism; segment memory by hand.

## Architectural reality check

| x86_64                                | Cortex-M3/M4                                                                 |
|---------------------------------------|-------------------------------------------------------------------------------|
| GDT / TSS / segments                  | Gone. Modes are Thread vs Handler; no segmentation.                          |
| IDT + `extern "x86-interrupt"`        | Vector table at start of flash, generated by `cortex-m-rt`.                  |
| 8259 PIC                              | NVIC, built into the core, exposed by `cortex-m`.                            |
| 4-level paging, `OffsetPageTable`, CR3 | No MMU. Optional MPU offers region protection only. Fits the "segment by hand" goal. |
| Port I/O (`in`/`out`, port 0xf4)      | All MMIO. QEMU test-exit uses **semihosting**.                               |
| `bootloader_api` BootInfo             | Memory layout fixed at link time via `memory.x`.                             |
| `hlt`                                 | `wfi` / `wfe`.                                                               |
| `bootimage` / BIOS disk image         | None. QEMU loads ELF directly via `-kernel`.                                 |

## Per-file disposition

From `kernel/src/`:

- **`gdt.rs`** — delete.
- **`memory.rs`** (paging + frame allocator) — delete.
- **`interrupts.rs`** — rewrite as `cortex-m-rt` `#[exception]`/`#[interrupt]` handlers + NVIC helpers. Wire **SysTick** first (built into every Cortex-M).
- **`serial.rs`** — rewrite as a UART driver behind a `core::fmt::Write` impl. See UART strategy below.
- **`qemu.rs`** — rewrite to `cortex_m_semihosting::debug::exit(...)`. Semihosting is for test pass/fail only; runtime output goes over UART.
- **`allocator.rs`** — keep `linked_list_allocator`; init from a static `[u8; N]`. Feature-gate so the no-alloc path is buildable by default.
- **`print.rs`** — keep the `println!` macro; point its writer at the UART.
- **`testing.rs`** + `kernel/tests/*` — keep harness structure; swap exit path to semihosting. Rewrite `stack_overflow.rs` as a **HardFault** test (Cortex-M has no double-fault).
- **`lib.rs` / `main.rs`** — replace `bootloader_api::entry_point!` with `#[cortex_m_rt::entry]`. `init()` shrinks to: UART → SysTick → (optional) heap.
- **Host runner** (`/src/main.rs`, `scripts/run-kernel-test.sh`, `build.rs`) — delete. Collapse into a cargo `runner` in `.cargo/config.toml`.
- **`memory.x`** — new file, lm3s6965evb layout (256 KiB FLASH @ `0x0`, 64 KiB RAM @ `0x2000_0000`). Per-board variant for STM32F429 later.
- **`flake.nix`** — swap targets to `thumbv7m-none-eabi` (+ `thumbv7em-none-eabihf` later). Drop `cargo-bootimage`. QEMU already covers `qemu-system-arm`. Add `probe-rs` when hardware appears.
- **`.cargo/config.toml`** — `target = "thumbv7m-none-eabi"`; runner `qemu-system-arm -cpu cortex-m3 -machine lm3s6965evb -nographic -semihosting-config enable=on,target=native -kernel`.
- **`.helix/languages.toml`** — retarget rust-analyzer (same workaround as today, new triple).

## UART strategy

There's no portable Cortex-M UART; abstract behind a trait so board swaps are cheap:

1. Define a small `Console: core::fmt::Write` (or just rely on `Write`) inside the kernel.
2. One impl per board, feature-gated:
   - **lm3s6965evb** (QEMU): Stellaris UART (~50 lines of MMIO).
   - **STM32F429ZI Nucleo**: USART3 (wired to the ST-Link VCP). Either `stm32f4xx-hal::Serial` or ~80 lines hand-rolled.
   - **LPC1768**: LPC UART0; hand-rolled or via `lpc176x-hal`.
3. `print.rs` holds a `static` initialised at boot; `println!` writes through it.
4. Use `hprintln!` (semihosting) only during the first bring-up before the UART works.

This abstraction is the only thing standing between you and a working STM32/LPC port later: new board = new `memory.x` + new UART impl.

## Crate diff

Remove: `x86_64`, `bootloader_api`, workspace `bootloader`, `pic8259`, `uart_16550`, `volatile` (unless used for hand-rolled MMIO).

Add: `cortex-m`, `cortex-m-rt`, `cortex-m-semihosting`, `panic-semihosting` (early) or `panic-halt` (later).

Keep: `linked_list_allocator` (feature-gated). `spin` works, but `critical-section` / `cortex-m::interrupt::Mutex` is more idiomatic — swap later if it bites.

## Ethernet feasibility (curiosity track)

Tractable, and **the no-Embassy preference doesn't block it**.

- `smoltcp` is the canonical no-std TCP/IP stack. It is **poll-driven, not async** — call `iface.poll(now)` from a main loop or a timer ISR. Embassy wraps it; you don't need Embassy.
- It talks to your MAC via a `Device` trait you implement (give it TX/RX buffers, it hands you packets).
- **QEMU `lm3s6965evb` emulates the Stellaris Ethernet MAC** (`stellaris_enet`) — full end-to-end prototyping without hardware. Use `-netdev user` for outbound, or a TAP for bridged.
- **STM32F429ZI Nucleo** has Ethernet MAC + LAN8742A PHY on board, and there's a maintained **`stm32-eth`** crate that already implements `smoltcp::Device` for it. Hard parts (DMA rings, PHY init) are done.
- **LPC1768** has a MAC but the mbed board lacks a PHY → dead-end for ethernet.

Rough cost once the kernel boots with timer + UART: ~1 week on QEMU (Stellaris MAC `Device` impl is the bulk); a few days on STM32F429 thanks to `stm32-eth`. The real risk to ethernet later isn't the no-Embassy choice — it's hardcoding the UART without an HAL boundary, which the UART strategy above prevents.

## Milestones (one commit each, mirroring the chapter cadence)

1. **Hello, UART on QEMU.** `cortex-m-rt` entry, Stellaris UART, `println!("hello")` visible via `-serial mon:stdio`, `wfi` loop.
2. **Tests under QEMU semihosting.** Custom test runner wired to `debug::exit`; UART for test output, semihosting for exit codes; a basic integration test in `tests/`.
3. **SysTick.** 1 kHz tick, `#[exception] fn SysTick()`, visible counter.
4. **Heap (optional, feature-gated).** `linked_list_allocator` over a static `[u8; N]`. Port `heap_allocation` test.
5. **Board abstraction.** Console trait + per-board UART; STM32F429 build target added (probe-rs flashing).
6. **(Curiosity)** smoltcp on the Stellaris MAC in QEMU: ping, then TCP echo.

Each milestone is independently bootable on QEMU. Estimated effort for milestones 1–4: ~2–3 focused evenings total. Milestone 5 is mostly mechanical once 1–4 are clean. Milestone 6 is its own week-long sub-project.

## Verification (overall)

- `cargo build` produces a `thumbv7m-none-eabi` ELF.
- `cargo run` boots under `qemu-system-arm -machine lm3s6965evb`, prints over UART, SysTick ticks.
- `cargo test` exits with the correct shell code via semihosting.
- A deliberate panic surfaces over UART and exits failure.
- A deliberate null-deref triggers the HardFault test.
- (Stretch) `cargo build --features stm32f429` produces an ELF flashable via `probe-rs run`.

## Real hardware: mbed NXP LPC1768

The LPC1768 reuses the `thumbv7m-none-eabi` triple; only the linker layout and the UART driver differ. The mbed's onboard interface MCU exposes both a CMSIS-DAP debug probe and a USB CDC ACM serial port (`/dev/cu.usbmodem*`). 9600 8N1, the mbed factory default.

```sh
# Build + flash + verify + reset via the mbed's DAPLink, then attach RTT.
./scripts/flash-lpc1768.sh

# In a second terminal, open the mbed's USB CDC port to see UART output:
screen /dev/cu.usbmodem* 9600   # or tio, picocom, etc.
```

Notes:

- `cargo run` and `cargo test` stay QEMU-only — they're the fast feedback loop. The LPC1768 path is a separate command when you actually want to flash hardware.
- We use **probe-rs** for flashing. probe-rs 0.31 doesn't ship a built-in LPC1768 chip definition (NXP coverage stops around LPC55xx / LPC54xxx), so we generate one ourselves from NXP's CMSIS-Pack and pass it at runtime via `--chip-description-path probe-rs-targets/LPC1700_Series.yaml`. The pack-derived flash algorithm (`lpc_iap_512`) handles the LPC vector-table checksum at offset `0x1C` for us. The YAML is checked in; regenerating it is a one-shot `target-gen pack` invocation against `Keil.LPC1700_DFP.*.pack`. One tweak on top of the generated YAML: we cleared the `access: execute: false` flag on the LPC1768's IRAM1, which is wrong as imported — IRAM1 is the CPU-local SRAM and probe-rs needs to execute the flash algorithm from there. (See the inline comment in the YAML.)
- **Cleanup quirk**: every successful `probe-rs download` / `probe-rs reset` against the LPC1768 ends with `Could not clear all hardware breakpoints` / `Failed to deconfigure device during shutdown`. The data is on the chip — the SWD link goes briefly flaky after the IAP flash algorithm finishes (or after a reset releases the core), and probe-rs's `session_drop` can't read back the FP_COMP registers. Functionally cosmetic; `flash-lpc1768.sh` swallows the non-zero exit with `|| true` on both calls. OpenOCD didn't surface it because it doesn't touch the breakpoint registers on shutdown.
- The kernel runs from the LPC1768's reset clock (IRC, 4 MHz). SysTick is configured for 1 kHz at that rate, so the tick rate is honest on hardware. Under QEMU the same reload value gives a slower emulated rate.
